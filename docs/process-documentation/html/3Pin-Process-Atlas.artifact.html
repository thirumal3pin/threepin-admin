    Functional overview

    What every console and process does, in one line each.

    The platform runs the whole property business in five consoles that share one sign-in, one navigation rail and one database. A property moves left to right through them: it is found (CRM), listed and shot (Shoot & Media), described and stored (Property dashboard), posted (Posting) and sold and billed (CRM and Finance).

    Business guide

    How each feature is used, and why at that point of the lifecycle.

    Every feature exists to remove one of four business risks: a lead nobody answers, a seller nobody lists, a property nobody can find the facts for, and money nobody tracks. This guide follows the business day and the property lifecycle, and for each feature says when to use it, how, and what it saves.

    How the property code travels

    1. A brochure request or Inventory sheet row creates the code (properties.propertyCode).
    2. An agent maps a Shoot & Media card to it by hand → listings.propertyCode.
    3. The board copies it to the seller's lead → leads.propertyCodes, listingCode.
    4. The AI adds it to buyer leads that discussed the property → leads.propertyCodes.
    5. Posting rows are keyed by it → postTracker.propertyCode; post URLs are saved there.
    6. A site visit on that code pulls the seller's name, number and location into the calendar invitation.
    7. A Finance deal copies it once.
    8. The dashboard reads cards, posts and leads back by the same code.

    Process 2 — Sync from the Inventory sheet

    1. Read the Inventory sheet and the Queue sheet (columns found by header text, never by letter).
    2. Build each row into a property. Column F packs type | sale type | stage | possession | age; the stage becomes the two-value status (Ready to Move / Under Construction) and the original wording is kept.
    3. Unknown headers go to From the Inventory Sheet (sheetExtras) automatically — a new column needs no code change.
    4. Empty cells never clear a value. Queue photos and details only fill blanks.
    5. Protection: any field with an un-ticked dashboard change is skipped, so the dashboard's value stays; a pending delete stops the property being recreated.
    6. Old properties with no sheet row are never touched.
    7. Preview first; apply writes a backup (syncBackups, or backups/ on the Mac) and then merges.

    Process 3 — Brochure pipeline (end to end)

    1. Submit on Create brochure (or the Shoot & Media board's brochure panel): "CODE - Title", Drive photo folder, property details, internal notes. The code assistant suggests the next free code, flags existing codes and near-misses.
    2. A row lands in the Queue sheet; the request is logged in brochureLog.
    3. Cowork (Claude on the owner's Mac) builds the PDF and sets the row to Done.
    4. The Mac's deliver-brochures job uploads the PDF to the photos folder in Drive, makes it link-readable, emails it to Thirumal, Swami and Pradeep ("Brochure ready: ID — title"), marks the Queue row Brochure Emailed, writes the link into the Inventory sheet's Brochure_Link, and creates / updates the property in the dashboard. Failures send a "[FAILED]" email (once per 24 h).
    5. Recent brochures shows In queue / Generated — being sent / Delivered / Needs attention.
    6. The Shoot & Media board sees the new property within seconds and links the card that asked for it.

    Process 5 — Copy dashboard edits back to the sheet (by hand, by design)

    There is no automatic write-back. The maintainer opens Changes to apply → Pending, makes the same change in the Inventory sheet, then ticks the row. Ticking hands that field back to the sheet: from the next sync, the sheet's value wins. Entries can never be deleted.

    Process 6 — Matching buyers and client briefs

    The match engine (shared with the CRM and the board) scores every buyer lead against the property in four layers: rule-outs (wrong type, a stated objection, sold out) → weighted attributes (Budget 28, Location 22, Configuration 16, Type 14, Size 10, Possession 9, Lifestyle 8, Amenities 6, Vastu 5, Approval 4, Facing 4, Builder 4, and smaller ones) → wording similarity → objection penalties. Bands: 85 %+ Strong match · 70 %+ Worth a call · 55 %+ Partial · below that Long shot. Matching Buyers lists them with Open in CRM and Call.

    Lead views (leadViews) — how the CRM opens cheaply

    Firestore bills one read per document, so a list of 760 leads used to cost 760 reads on every open. Since 13 Oct 2026 every lead also lives as a row inside a view document holding about 20 of them: leadViews/{tenant}__meta (layout: version, shard count, count, built time, off switch) and leadViews/{tenant}__v{n}_{i} (rows: { leadId: lead + _w }). The CRM, dashboard and board read the views — 39 reads instead of 760 — and then one read per change, as before.

    • A row is the lead (same fields; notes and history stay in their sub-collections), so every screen reads it exactly as it read the lead.
    • Every writer — CRM, board, dashboard, TailorTalk sync, AI, calendar — writes the lead and its row in the same batch or transaction, stamped with the server's time (_w). A page saves only the fields it changed, so a row that was behind can never carry an old value back into a lead.
    • The 09:00 digest rebuilds the views from the leads themselves, keeping any row written after the leads were read; when the leads outgrow the documents a larger set is prepared and switched to a day later.
    • Switches: node scripts/lead-views.mjs verify (must print "IN STEP"), build, off (every page reads the leads directly again, within seconds — the kill switch), on.

    3D · Finance — the agency's own books

    Console: 3pinfinance.html (/3pinfinance). Data: everything under finance/{tenant} — settings, txns (the ledger), parties, deals, invoices, bills, subscriptions, loans, assets, bankStatements, monthEnds.

    Finance keeps 3 PIN Realty's own accrual-basis, double-entry books. Nobody needs to know accounting: the user picks a plain-language action ("Token received", "Invoice the buyer", "Bill received — pay later", "Pay an EMI"), and the app builds a balanced journal against a fixed chart of 63 accounts, plus any bills, invoices, deals, recurring costs, loans or assets it implies — all in one transaction with gapless numbering. Every report is derived live from the ledger.

    StepActionWhat the books record

    "Settled" is worked out, not stored: registered, invoiced, nothing owed, nothing held.

    Process 2 — Costs, from estimate to settled

    1. Expense (paid now) or Bill received — pay later (creates a bill due in 30 days). "Which month is this cost for?" books it to the right period.
    2. Bill arrived adds the vendor's bill number to an accrual and releases parked GST credit.
    3. Pay a bill — oldest first; TDS withheld; a let-off amount reduces the cost.
    4. Other actions: petty-cash vouchers, director paid, salary (gross, net, TDS, PF/ESI), buy an asset, sell/scrap an asset, vendor refund.

    Process 3 — Recurring costs, loans, month-end

    • Recurring: set up a service (monthly or paid upfront); each month Record this month (paid / not paid yet / skipped), with the variance and its reason; change, pause or cancel (unused prepaid refunded or lost).
    • Loans: EMI schedule; Pay an EMI splits principal, interest, charges, penalty; prepayment rebuilds the schedule; card-to-EMI conversion.
    • Month-end (by hand): posts prepaid releases and depreciation; asks for a reconciled bank statement first (override recorded).
    • Bank reconciliation: import a statement → auto-match within ₹1 and ±3 days → suggested entries for unmatched lines (learned rules, ATM = petty top-up, card bill, open bill, EMI, invoice…) → Save reconciliation.

    Process 4 — Fixing mistakes

    The ledger is append-only (enforced by the database rules). A mistake is fixed with Reverse: a mirror entry that unwinds payments, voids bills it created and issues a credit note for any invoice it raised. It is refused once an invoice or bill has payments against it.

    Database rules (Firestore ruleset 132b5f73, deployed 13 Oct 2026)

    Every read and write is checked against the caller's tenant. Points worth knowing:

    • Leads: a team member may get or delete a lead that does not exist (so a page can tell "deleted" from "not yours"), but for TailorTalk ids — tt_<tenant>_<id>, which can carry a phone number — that answer is given only for the caller's own tenant's ids, so nobody can test whether a number is another tenant's lead. Listing leads needs the tenant field; an update may never move a lead to another tenant.
    • Lead views: readable by the tenant's team. A page may create or update a view document only with the keys tenantId and rows, touching one row per write — so no page can rewrite or empty a whole document. The meta record and the daily rebuilds are the server's (Admin SDK).
    • Finance ledger (txns): a new entry must balance (debits = credits), carry at least one line and be dated on or after the books' start date; an entry is never deleted — only reversedBy and the reconciliation marks may change. The finance settings record (finance/{tenant}, including the Drive folder id) is readable and writable by any team member.
    • Property change log (propertyChanges): append-only.
