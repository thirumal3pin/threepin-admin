Deliver leads into the 3 PIN Realty CRM over HTTP, and receive pipeline status back as the sales team works them.

Introduction

3 PIN Realty operates a real-estate CRM at admin.threepin.in. Leads arrive on a pipeline, are assigned to an agent, and move through stages until they close. Today they come from three sources: entered by an agent, captured by the WhatsApp assistant, or pulled from Meta Lead Ads. This API adds a fourth — leads delivered by an integration partner.

The integration has two halves. You send us leads, one per request, signed with a shared secret. We send you status updates as those leads progress. Both directions use the same signature scheme, so a single verification routine serves both.

How a lead flows

Lifecycle
Your system captures an enquiry
  → POST /api/partner-leads (signed)
  → signature and timestamp verified
  → phone normalised, checked against existing leads
  → lead created, or merged into the existing record
  → appears on the agent board in real time
  → POST to your callback URL on every stage change

Do not send leads to the Meta webhook

/api/meta-webhook is a Meta-specific route. It verifies a signature generated with Meta's own application secret, and accepts only a Meta leadgen_id which it then resolves through the Meta Graph API. It cannot accept a lead from any other source, and the credential required to call it is not one we can share.

Authentication

Every request is signed. There are no API keys in query strings, and no bearer tokens for partner traffic.

We issue two values out of band. The signing secret is a credential: it must never appear in a URL, a log line, or any client-side code.

ValueExampleUse
partnerIdtp_acmeSent as a header. Identifies you and selects your secret.
signingSecretwhsec_…Never transmitted. Used only to compute the signature.

Request headers

HeaderValue
Content-Typeapplication/json
X-3Pin-PartnerYour partnerId
X-3Pin-TimestampUnix time in seconds at the moment of signing
X-3Pin-Signaturesha256= followed by the lowercase hex digest

Computing the signature

The signed message is the timestamp, a literal full stop, then the exact raw request body:

Base string
signature = "sha256=" + HMAC_SHA256(signingSecret, timestamp + "." + rawBody)

Sign the bytes you send

Parsing JSON and re-serialising it changes key order and whitespace, which changes the digest. Build the body string once, sign that string, and transmit that same string. A re-serialised body is the most common cause of a rejected signature.

Including the timestamp in the signed message is what makes a captured request non-replayable. We reject any request whose timestamp differs from ours by more than 300 seconds, and compare digests in constant time.

Node.js
import crypto from 'node:crypto';

const secret = 'whsec_3pin_demo_do_not_use';
const timestamp = String(Math.floor(Date.now() / 1000));

// Build the body once, as a string. Do not parse and re-stringify it.
const rawBody = JSON.stringify({
  event: 'lead.created',
  idempotencyKey: 'tp_9f2c41d8',
  lead: {
    name: 'Anitha Raghavan',
    phone: '+91 99418 80088',
    channel: 'facebook',
    enquiryType: 'Property Enquiry',
    propertyInterest: 'Oragadam Plots - Phase 2',
    budget: '45 to 60 L'
  }
});

const signature = 'sha256=' + crypto
  .createHmac('sha256', secret)
  .update(timestamp + '.' + rawBody)
  .digest('hex');

await fetch('https://admin.threepin.in/api/partner-leads', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-3Pin-Partner': 'tp_acme',
    'X-3Pin-Timestamp': timestamp,
    'X-3Pin-Signature': signature
  },
  body: rawBody // the same string that was signed
});
Python

secret = b'whsec_3pin_demo_do_not_use'

    "idempotencyKey": "tp_9f2c41d8",
    "lead": {

    },
    timeout=15,
)

If your digest differs

Compare the byte length of your body first. The rawBody above is shown wrapped for readability but is a single line of 237 bytes. A trailing newline, a pretty-printer, or a byte-order mark will each change the result.

Create a lead

One lead per request. The response tells you exactly what happened to it; there is nothing to poll.

POST /api/partner-leads Planned
Request body
{
  "event": "lead.created",              // required, only value today
  "idempotencyKey": "tp_9f2c41d8",      // required, unique, max 128 chars
  "sentAt": "2026-09-02T09:14:22.000Z", // optional, ISO 8601

  "lead": {
    "name":             "Anitha Raghavan",          // required
    "phone":            "+91 99418 80088",          // required
    "channel":          "facebook",                 // required
    "enquiryType":      "Property Enquiry",         // required
    "propertyInterest": "Oragadam Plots - Phase 2", // required

    "email":            "anitha.r@example.com",
    "budget":           "45 to 60 L",
    "notes":            "Prefers a site visit on Sunday.",
    "contactAt":        1772442000000,             // epoch milliseconds

    "campaign": {
      "name":     "Oragadam Plots - Sep",
      "adId":     "238471193",
      "adsetId":  "238471100",
      "platform": "facebook"
    },

    "raw": {                                  // free-form, stored verbatim
      "plot_size": "1200 sqft",
      "timeline":  "3-6 months"
    }
  }
}

Five fields are mandatory

name, phone, channel, enquiryType and propertyInterest. This mirrors exactly what the CRM's own lead form requires, so a partner-supplied lead is never less complete than one an agent typed. If your source genuinely has no property, send the campaign or landing-page name rather than an empty string — propertyInterest is the field agents work from.

All three results are success

Treat created, merged and duplicate identically in retry logic — the lead is with us, stop retrying. Only a 5xx or a network failure warrants another attempt.

Timestamps are epoch milliseconds

Integers, not seconds and not ISO strings. The one exception is sentAt on the envelope, which is ISO 8601 and informational. Sending seconds where milliseconds are expected dates the lead to January 1970 and sorts it to the bottom of every view.

Value handling

Two fields are transformed on arrival. Both tables below are observed output from the CRM's own functions.

Phone numbers

A canonical key is derived for duplicate matching only. The number you send is what is stored and displayed — normalisation never rewrites it. Bare ten-digit numbers are assumed Indian.

SubmittedMatching keyRule
9941880088919941880088Ten digits, prefixed with 91
09941880088919941880088Leading zero removed, then prefixed
+91 99418 80088919941880088Non-digits removed
919941880088919941880088Already canonical
+1 415 555 012314155550123Non-Indian numbers kept as given

All four Indian formats collapse to one key, so a lead you send as +91 99418 80088 correctly matches one an agent typed as 9941880088. Send whatever format you hold; E.164 is preferred but not required.

Budget

Budget feeds the open pipeline value, which the business manages against. Values are normalised into the CRM's own notation before being parsed.

SubmittedNormalisedCounted as
₹30–50 Lakhs30 to 50 L₹40 L
Below ₹25 Lakhs25 L₹25 L
3 - 5 Crores3 to 5 Cr₹4 Cr
₹70 Lakhs+70 L₹70 L
Above 5 Cr5 Cr₹5 Cr
1.5 Cr1.5 Cr₹1.5 Cr

Always send a unit

A budget without L or Cr is dropped from pipeline value without an error. 12000000 parses to null, and ₹1,20,00,000 normalises to the unusable string 1 20 00 000 because thousands separators become spaces. Neither case is visibly wrong on the record; the value simply never reaches the total.

1.2 Cr works. 12000000 does not. A range such as 45 to 60 L is averaged. Convert raw integers before sending.

Duplicates

Two independent mechanisms: one protects against your retries, the other against the same person enquiring twice.

Idempotency key

Generate one stable, unique key per lead and reuse it across every retry of that lead. If we have already processed the key we return result: "duplicate" with the original lead ID and change nothing, so a network timeout is always safe to retry. Keys are scoped to your partner ID and only need to be unique within your own system — your own primary key is usually the right value.

Phone matching

Before creating anything we look for an existing lead with the same normalised phone key. If one exists we merge rather than create, because a second record for the same person is work an agent then has to undo by hand.

Merging only fills blanks

We populate email, budget and propertyInterest only where the existing record has no value. We never overwrite what an agent entered, never move a lead back to new, and never clear a scheduled follow-up. The merge is written to the lead's history, and the merged array in the response lists exactly which fields were filled.

A 4xx will not succeed on retry

Retrying a 400 or 401 unchanged consumes capacity on both sides and will trip the rate limiter. Send those to a dead-letter queue and alert someone. Only 408, 429 and 5xx are worth another attempt.

Status callbacks

So you can measure lead quality without asking us for a report.

POST https://your-endpoint.example.com/… Planned

Give us one HTTPS endpoint. We post to it whenever a lead you supplied changes stage, and when it closes. We sign with the same scheme you use — same header names, same base string — so your verification code works in both directions.

Callback payload
POST https://your-endpoint.example.com/3pin/leads
X-3Pin-Partner: tp_acme
X-3Pin-Timestamp: 1772449001
X-3Pin-Signature: sha256=<digest of timestamp + "." + body>

{
  "event": "lead.stage_changed",
  "sentAt": "2026-09-02T11:03:21.000Z",
  "leadId": "partner_tp_acme_9f2c41d8",
  "idempotencyKey": "tp_9f2c41d8",  // your key, echoed back
  "from": "new",
  "to": "contacted",
  "changedAt": 1772449001482,
  "reason": null
}
EventFires when
lead.stage_changedAn agent moves the lead between any two stages.
lead.closed_wonThe lead reaches closed_won.
lead.closed_lostThe lead reaches closed_lost, with a reason where recorded.

Requirements for your endpoint

  • Return a 2xx status. Anything else counts as a failure.
  • Respond within 10 seconds, then process asynchronously.
  • Be idempotent — deduplicate on leadId together with changedAt.
  • Verify our signature before trusting the body.

On failure we retry three times with exponential backoff, roughly at one minute, five minutes and twenty-five minutes. After that the event is dropped and logged. There is no replay queue, so a prolonged outage means permanently missed events.

There is no reconciliation sweep for partner leads

The Meta integration has one because Meta retains a copy we can re-read. We will never hold a copy of a lead you failed to deliver. Your retry logic is the only safety net — if a submission exhausts its retries, alert someone rather than dropping it.

Data model

Included so you can reason about what happens to a lead after we accept it. Partners have no direct database access.

CollectionHolds
leadsThe lead record, with a tenant identifier on every document.
leads/{id}/notesNotes as a subcollection, so adding one does not rewrite the lead.
leads/{id}/historyAppend-only audit trail of every field, stage and follow-up change.
pipelinesThe ordered stage list, configurable per business.
settingsEnquiry types, known properties, digest recipients.

Every document carries a tenant identifier, and access is scoped to it. Your leads are written under the 3 PIN Realty tenant and are not visible to any other. Notes and history are append-only: neither your submission nor an agent's edit erases what came before, so the provenance of every field remains auditable.

Integration checklist

Every item is verifiable; none depend on judgement.

Your side

  • Signer reproduces the test vector digest exactly.
  • The body you sign is the body you transmit, with no re-serialisation between.
  • All five required fields are populated on every lead, with no empty strings.
  • channel is one of the four accepted values.
  • Budgets carry an L or Cr unit, never a bare integer.
  • Timestamps are epoch milliseconds.
  • Idempotency keys are stable across retries and unique per lead.
  • Retries cover only 408, 429 and 5xx.
  • Callback endpoint returns 2xx within ten seconds and verifies our signature.
  • Callback handling is idempotent.
  • Servers are synchronised to NTP.
  • A dead-letter queue exists and alerts a person.

Our side

  • /api/partner-leads deployed.
  • Partner identifier and signing secret provisioned.
  • Callback URL registered.
  • Stage-change events firing.
  • Ten-lead end-to-end test passed, including a deliberate duplicate and a deliberate merge.
